## 结论与接受范围

本机完成一次“目标聊天行明确菜单 → 准确原聊天新窗口 → 最小化 → fresh IPC 查询”的监督链路。新窗口自身的 RootWebArea URL 含 `/local/<指定原聊天ID>`，并显示对应聊天标题；因此准确归属并非从旧 owner 仍可访问而反推。主窗口在开窗前后均保持当前发起聊天，未导航到目标。最小化后准确 target/cwd 的原生快照为 idle，owner 与前态相同。

本轮只有一次开窗、一次最小化、零模型任务、零 watcher 启动和零业务 ACK。这是当前安装版本、已加载目标、受监督条件下的窗口链路证据。尚未实现可部署的窗口后端，也不能据此验收冷恢复、完全后台创建或无人值守业务。

## 失败、纠正与输入保全

准备期的截图与 UIA 曾不一致，主窗口也在用户活动期间变化；未据此判定上轮切换原因。用户明确同意短时不操作后，采用稳定的发起聊天画面作为本次基线；菜单打开后再次读取，UIA 与画面恢复一致。首次菜单后即时截图尚未显示菜单，下一次只读刷新才确认菜单，没有连续盲点。

默认沙箱 IPC 探针在发送方法前失败；经过已批准的窄范围执行，前后只读探针均成功，没有修改 ACL 或全局配置。初次 Git fetch 遇 DNS/连接重置，故先建立固定提交的隔离输入并验证清单；稍后 HTTP/1.1 fetch 成功，补核全部 57 个 Git blob。原 clone HEAD 仍在其既有版本及五份准备文件，未 checkout、reset 或覆盖用户修改。

## 给爱丽丝的判定清单

| 已解决或本轮可确认 | 仍需后续实现或验证 |
|---|---|
| 当前 UI 有明确目标行开窗入口，无需猜 Ctrl 修饰键 | 自动加载器尚无该入口的可靠后端；默认关闭保持 |
| 新窗口 URL 可提供准确 target 绑定，再选择该窗口最小化 | GUI 自动化在 UIA 延迟、布局/DPI/语言变化下的鲁棒性未验 |
| 本次主窗口当前聊天保持，原聊天最小化后仍可查询 | 自然 notLoaded → owner 恢复、长期保活、关闭或重启后的生命周期未验 |
| 接受短暂前台显示即可完成本次监督链路 | 零聚焦创建、严格焦点上界及任意原应用恢复未解决 |
| 前后 fresh IPC、相同 owner 和精确目标/cwd 可交叉核对 | 新窗口本身是否承载 owner 未独立映射，不能由“同 owner”推出 |

建议接受这一有限窗口链路结果。若继续，下一步是将已证实的明确菜单路径做成单独、默认关闭的有界后端：仍先复用已有 owner；需要动作时识别准确目标行，仅开一次，验证新窗口 route 后再最小化，再 fresh 查询。该建议不授权本轮继续实现、接入 watcher、冷启动、模型发送或恢复原 timer。需要冷恢复证据时等待自然未加载条件，不人为卸载现有聊天。
