## 当前目标与动作时点

将红魔所说的“关闭”实现为**正常关闭程序创建、且此刻仍能准确关联到原聊天的专用窗口**。主应用和文件监听器继续运行；不退出整个应用、不删除或归档聊天。任务运行期间先最小化，任务完成且核验回执后才关闭。最小化已经取得本轮有限证据；关闭后的 owner 生命周期仍需测量。

[官方 Commands](https://learn.chatgpt.com/docs/reference/commands) 把关闭当前窗口/标签与退出应用列为不同操作；该页没有保证关闭窗口后原聊天 owner 保留。不能从普通深链接或云端任务可后台执行推断这个 Windows local 聊天的行为。

| 新批次触发后的 fresh 查询 | 拟实现动作 |
| --- | --- |
| 准确目标/cwd 的 owner 存在且 idle | 直接复用，无需新开或激活窗口 |
| owner 存在但 busy | 保留批次等待，不打断原回合，不另开来绕过忙碌 |
| 明确 owner 缺失 | 调用已验证的目标行“在新窗口中打开”路径；准确绑定后最小化，再 fresh 查询目标/cwd/idle |
| 查询失败、身份不匹配或状态不明 | 保留待处理状态，报告实际原因；不等同于“未加载”并盲目开窗 |

发送仍沿用已有固定批次和发送意图。完成路径为：**关联本批回合完成 → 核验业务结果并登记 delivered → fresh 空闲/窗口归属检查 → 关闭本程序专用窗口 → 记录关闭结果**。accepted、当前 idle、窗口消失中的任何一个都不能独自替代交付回执。

这轮明确的循环目标取代前轮“成功后一直保留最小化窗口、不主动关闭”的试验收尾限制。可正常关闭本试验创建且重新确认归属的专窗，测量关闭后的状态；不再要求仅为这个关闭循环等待自然 notLoaded。关闭后 owner 仍在则下次复用；确实缺失才测试重新加载。若未出现 owner 缺失，不能声称已通过冷恢复。

1. **独立窗口后端。** 将已经证实的准确目标行菜单路径做成有界脚本/适配器，复用现有可用工具，不新建窗口控制框架。以该窗口自身 route 和唯一窗口标识关联目标；opaque ID 不冒称 HWND。普通深链接不能替代保留主窗口聊天的要求。自动化实现应处理本轮实际遇到的 UIA 刷新延迟，不按固定坐标连续盲点；找不到明确入口或准确新窗口时停止本次动作。
2. **接入待处理批次。** 只有需要投递的未发送批次才检查/准备 owner；没有材料时不打开窗口、不产生模型任务。复用前述四类判断和单 worker 串行机制。观察忙碌与执行中的回合继续走现有路径，不因开窗/关闭逻辑重发。
3. **允许逐轮使用。** 当前 `owner_load_attempt:<thread_id>` 永久一次的预算不能支持此循环。改为持久的逐轮开窗额度：本轮动作前先登记，超时或结果不明不能由下一次扫描、新文件或进程重启重置；只有前轮明确结束并完成必要窗口对账后，才允许新轮再次开窗。可复用已绑定窗口时不再创建。保留旧 claim 的追溯与未完成状态，不靠删除状态库解锁。
4. **明确窗口由谁管理。** 持久保存本程序实际创建的专窗关联，关闭前重新核对。复用其他已有 owner 不等于获得关闭其用户窗口的权利；主窗口及非本程序窗口不自动关闭。若专窗已被用户改到别的聊天、标识过期或再次 busy，等待或报告，不关闭错误对象。重启后窗口身份不明时先对账，不把任意新 ID 当成旧窗口。
5. **在可靠完成点收尾。** 沿用现有结果核验/ACK 接口。当前 `Store.acknowledge` 只是保存调用者核验声明，并非自动业务核验器；窗口后端不得自己因 accepted、idle 或 task_complete 填 delivered。真实业务若仍需人工登记回执，要如实保留该依赖；不为本轮扩建通用业务审查器。登记交付和关闭调度需按现有 worker 机制协调，避免下一批刚启动就关闭窗口。关闭失败只留下窗口清理状态，不撤销已核验交付、不重发本批；下次先核对已有窗口和 owner。
6. **关闭后读一次实际状态。** 确认该专窗已关闭及主窗口聊天保持，再查询目标 owner 的真实状态；把“仍存在”“已缺失”“查询不明”分开记录。owner 存活不是关闭验收必须失败，缺失也不是交付失败。主应用继续运行，不 kill 进程，不注入受信内部消息。

默认关闭的加载开关可延续；窗口循环的启用和结果应在现有配置/日志中清楚可见。无需以绝对零聚焦、任意语言/DPI/版本全覆盖或长期保活作为本轮前置门。如观察到版本变化导致已验证入口失效，再针对实际差异处理。
